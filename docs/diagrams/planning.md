# Project planning — PERT, critical path and the 16-week Gantt

This file is generated by `docs/diagrams/make_behavioural.py`. Every number in
it is computed by that script at run time — the three-point estimates in the
table below are the only inputs, and the forward pass, backward pass, slack and
critical path are all derived from them. Re-running the script reproduces this
file byte for byte.

## 1. Method

Three-point (PERT) estimation over ten activities that match the delivered
modules: `app/rules.py`, `app/parser.py`, `app/engine.py` +
`app/openai_compat_provider.py`, `app/main.py`, `app/github_client.py`,
`benchmarks/`, `tests/` and the documentation pack.

* Expected time: `te = (O + 4M + P) / 6`
* Variance of one activity: `var = ((P - O) / 6)^2`
* Forward pass: `ES = max(EF of predecessors)`, `EF = ES + te`
* Backward pass: `LF = min(LS of successors)`, `LS = LF - te`
* Total float: `slack = LS - ES`; an activity with zero slack is critical
* Project duration: `max(EF)` over every activity

All times are **working days**, at 5 days per week, which puts
the 16-week frame of `docs/learning/PACE.md` at
80 working days.

## 5. Gantt assumptions

* The chart spans 16 weeks, the frame set by `docs/learning/PACE.md`.
* One week is 5 working days; a bar runs from `ES / 5` to
  `EF / 5` in week units, so a bar's right edge is the activity's earliest
  finish, not a calendar date.
* Activities are drawn in the order of the table, which is a topological order,
  so a successor never appears above its predecessor's start.
* Bars on the critical path are outlined in red; bars with float are outlined
  grey. The shaded band from the critical-path finish to week 16 is plan buffer
  and carries no activity — `PACE.md` keeps week 8 empty on purpose, and this
  chart shows the same idea as one contiguous tail.
* Milestones M1-M6 sit at the earliest finish of the activity that closes them:
  M1 design frozen (B), M2 rules and parser green (C), M3 provider layer green
  (E), M4 posting and benchmark green (G), M5 test suite green (I), M6 report
  and release (J).
* Completion state: the solid fill marks an activity that `CHANGELOG.md`
  records as delivered. Every activity carries it, because the changelog records
  all six phases complete on 2026-11-13/14 — the build ran as one continuous
  session, far inside the 16-week frame. Requirements (A) and design (B) are not
  logged as separate phases in the changelog; they are shown complete because
  Phase 1 could not have been built without them.

## 6. Plan versus record

The 16-week schedule in this file and in `gantt-chart.png` is **a plan, not a
record of what happened**. It states how long each activity was expected to
take, which activities could slip without moving the end date, and where the
buffer sits. Actual completion is recorded in `CHANGELOG.md`, which is the only
authority on what was delivered and when: it logs the six phases, the test count
at the end of each, and the dates. Where the two disagree, the changelog wins —
the plan is the estimate made before the work, and the estimates above were
written to describe the shape of the work, not to match a stopwatch. The
schedule should therefore be read as a statement about dependency and float,
and the changelog as the statement about outcome.

Two honesty notes on the figures:

1. **Reviews are persisted.** Every surface — `/review`, `/test-review` and
   `/webhook` — funnels through `_build_response` in `app/main.py`, which calls
   `_persist_review` and therefore `Database.store_review` in `app/db.py`: the
   SQLite store whose DDL is `SCHEMA_SQL`, six tables, drawn as Figure 4.
   Storage is best-effort by design: `_persist_review` and `_persist_pr_post`
   swallow every failure, log once at WARNING on `reviewer.db`, and leave the
   response exactly as it would have been; a blank `DATABASE_PATH` switches
   history off entirely. The `Review store` lifeline in the sequence diagram is
   that store, and a posting outcome is stored separately by
   `Database.store_pr_post`.
2. The webhook always answers GitHub with HTTP 200, even when the post failed —
   the locked Phase 5 decision, stated in the `app/main.py` module docstring.
   The state diagram therefore has `Failed` as a terminal *posting* state, not
   as an HTTP error.
